# Stage 4 final-review fix wave — 2026-10-09 10:04

Supplements `.claude/2026-10-09_0930_CHANGELOG.md`. After that change log was
written, the final whole-branch review (required before merging Stage 4)
found issues the per-task reviews had missed, including a safety-critical
one. This entry documents the fix wave that resolved them.

## What the final review found

1. **(Safety-critical)** `tests/test_cross_feature_integration.py` was
   silently making real `ydotool type` and `notify-send` calls on
   whoever's machine ran the suite. `build_dictation()`'s real
   `TextOutput` and every builder's real `Notifier` were never faked in
   several of the six new tests. This happened for real on the
   development machine every time any task's implementer or reviewer ran
   this file earlier today — the user was told directly and asked to
   check for stray "fake transcription" text in whatever window had
   focus. No file was deleted or corrupted; typed text had no Enter
   keypress, so nothing could have executed on its own.
2. The settings-propagation test rebuilt `DocumentReaderFeature` fresh
   after each settings change, so it never actually proved a live
   setting change reaches an *already-built* reader.
3. Three Minor documentation/assertion-tightening items.

## What the fix wave did

- Added an autouse `pytest` fixture (`_never_touch_real_hardware`) to
  `tests/test_cross_feature_integration.py` that patches `subprocess.run`
  to raise loudly if any test — this one or a future one — ever invokes
  `ydotool`, `xclip`, or `notify-send` for real.
- Added `_FakeTextOutput` and patched `vocalis.cli.TextOutput` /
  `vocalis.cli.Notifier.notify` in every test that needed it.
- Found and fixed a **second** leak not in the original review: the
  background "Done" notification thread Quick Reader/Document Reader
  spawn could finish *after* a test's `with patch(...)` block had already
  exited, letting a real `notify-send` through intermittently. Fixed by
  waiting for those threads to finish inside the patch block; the guard
  fixture itself now also fails a test that leaves a thread running.
- Rewrote the settings test to build the reader once and read twice on
  the same instance.
- Tightened the notification test to the exact message sequence, added a
  distinct-key-codes check to the hotkey test, corrected two inaccurate
  sentences in `docs/developer-docs.md`.

## Verification

The fix was verified twice, independently, by two different reviewers
each breaking a *different* test than the other and confirming the guard
fixture caught the real call before it reached the real desktop (plus a
separate process-launch spy plugin recording zero forbidden launches
across 8+ clean runs). Full suite: 607 passed, 96.75-96.78% coverage
(stable across the fix), zero warnings, mypy clean on 93 files.
