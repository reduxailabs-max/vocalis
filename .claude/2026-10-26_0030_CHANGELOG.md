# Stage 6d — Resource limits: change log

Branch `worktree-stage6d-resource-limits`. Plan and per-task reports:
`.superpowers/sdd/2026-10-25-vocalis-stage6d-resource-limits/`.

Stage 6c made Vocalis's voices sound better. Stage 6d is about Vocalis
being a better neighbor on your PC — letting you tell it "don't use more
than this much processor power / memory / graphics-card memory", so it
doesn't hog your computer while you're trying to do other things with it,
and so it steps back gracefully instead of crashing if it ever gets close
to those limits.

## What changed, and why

1. **Three new settings to limit how much of your PC Vocalis uses.** In
   the Settings window you can now set:
   - **Max CPU threads (0 = no limit)** — caps how many processor
     "workers" the voices use at once.
   - **Max RAM, MB (0 = no limit)** — a soft guideline for how much memory
     Vocalis itself should try to stay under.
   - **GPU VRAM ceiling, MB** — caps how much graphics-card memory the two
     GPU-capable voices (Qwen3-TTS and Kokoro) are allowed to use (default
     6144 MB / 6 GB; this one is always a real limit, there is no "0 means
     off" for it).

   All three take effect without restarting Vocalis — change them, hit
   Save, and the very next time a voice loads or speaks it uses the new
   numbers.

2. **Each voice applies the CPU and graphics-card limits its own way,**
   because each voice is built on different underlying software:
   - **Qwen3-TTS** (the best-quality voice) tells its underlying AI library
     (PyTorch) directly how many processor threads and how much
     graphics-card memory to use, each time it loads.
   - **Kokoro** (the middle voice) does the same thing, but through its
     own underlying library (ONNX Runtime), which has its own way of being
     told these numbers.
   - **Piper** (the lightest voice, CPU-only) is a bit of a special case:
     the actual Piper program that Vocalis runs has **no setting at all**
     for limiting how many threads it uses — we checked its own `--help`
     text to be sure. The only thing Vocalis can do is set two
     environment variables (`OMP_NUM_THREADS` / `ORT_NUM_THREADS`) before
     starting it, which some programs respect and some don't. Piper
     doesn't document whether it honors them, so **this is best-effort
     only** — Vocalis asks nicely, but can't force Piper to obey the CPU
     limit the way it can force Qwen3-TTS and Kokoro to obey it. This is
     re-applied every single time Piper speaks, since Piper doesn't stay
     "loaded" between sentences the way the other two voices do.
   - The graphics-card memory limit is best-effort on the GPU voices too,
     in one specific sense: if Vocalis can't even ask the graphics card how
     much memory it has (a failed check), it just logs a warning and lets
     the voice load anyway, rather than refusing to start the voice at all.

3. **The "Max RAM" limit is a gentle guideline, not a hard wall.** Vocalis
   will never crash itself or forcibly throw away memory just to stay
   under the number you set. Instead, it quietly folds this limit into the
   same "is my PC busy right now?" check that "Automatic" voice selection
   already uses: if Vocalis's own memory use goes over your limit,
   Automatic treats that exactly like a busy processor and switches to a
   lighter voice. To make that check work, Vocalis now reads its own
   *current* memory use (not its highest-ever use) straight from the
   operating system every time it checks.

4. **Automatic voice choice now waits a bit before switching back up to a
   better voice.** If Automatic had to switch down to a lighter voice
   because your PC looked busy, it now keeps using that lighter voice for
   a full 60 seconds, even if your PC looks free again moments later. This
   stops Vocalis from flickering back and forth between voices (and
   reloading them, which takes a moment) when your PC's load is jumping
   around right at the edge of "busy" and "not busy". This only affects
   **Automatic** — if you've picked a specific voice yourself in Settings,
   this waiting rule never applies to you.

5. **Vocalis now asks to run at a slightly lower priority on your
   computer.** The background service definition that starts Vocalis
   automatically (`vocalis.service`) now includes a "please go easy on CPU
   time compared to other programs" instruction (`Nice=10`), so Vocalis
   competes a little less aggressively for the processor against whatever
   else you're running.

6. **A more thorough memory clean-up when a voice is unloaded.** When
   Vocalis finishes using a voice model and unloads it to free up memory,
   it now also runs Python's own extra garbage-collection pass right
   afterward. This catches memory that could otherwise get "stuck" a
   little longer than necessary due to the way some objects reference each
   other internally, so memory is freed more promptly and reliably.

## Docs updated (this task)

- `docs/architecture.md` — new "Stage 6d addition: resource limits"
  section: the three settings, how each voice applies its CPU/VRAM caps,
  the advisory RAM-stress signal, the downshift hysteresis rule, the
  `Nice=10` systemd change, and the `gc.collect()` addition on unload.
- `docs/algorithms.md` — new "Auto-selection policy and downshift
  hysteresis" section, documenting `auto_select.decide()`'s existing rules
  alongside the new `EngineSelector._apply_hysteresis()` mechanics (tier
  ranking, the 60-second hold window, and that it only affects Automatic).
- `docs/user-docs.md` — plain-English descriptions of the three new
  Settings controls (including that Piper's CPU cap is best-effort and
  why), a short non-technical note in "Voice engines" about Automatic
  waiting before switching back to a better voice, and the three new
  fields added to the hand-editable `config.toml` reference list under
  "Configuration".

This task is documentation only — no source code was changed, so the
project's test suite and coverage are unaffected. See the branch's final
verification (run once, across all ten previous tasks plus this one)
for the actual `pytest`/`mypy` results before this branch is merged.
