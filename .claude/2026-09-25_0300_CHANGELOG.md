# Changelog — 2026-09-25 (Phase 3)

## Vocalis Phase 3: Quick Reader (TTS)

Pressing Ctrl+Alt+R now reads the clipboard aloud, with a real local AI
voice and an always-available backup voice.

**Added:**
- `vocalis.engines.qwen3_tts.Qwen3TTS` — primary voice, wraps the
  `qwen-tts` package's CustomVoice model (preset voice "Ryan" by
  default, no reference-audio/cloning step). GPU-only, managed through
  the existing `ModelManager` exactly like Parakeet.
- `vocalis.engines.piper_tts.PiperTTS` — fallback voice, wraps the
  already-installed local `piper` binary. CPU-only, never GPU-managed;
  loaded once at startup and always available.
- `vocalis.audio.playback.AudioPlayer` — sounddevice-based, interruptible
  speech playback (not a `pw-play` subprocess).
- `vocalis.hotkeys.ctrl_alt_r.CtrlAltRListener` — evdev-based Ctrl+Alt+R
  detection, built the same way as `NumlockListener`, applying Phase 2's
  Task 9/Task 10 lessons (per-callback exception isolation, ydotoold
  device exclusion) from the start.
- `vocalis.output.clipboard.ClipboardReader` — reads clipboard text via
  `xclip`.
- `vocalis.features.quick_reader.QuickReaderFeature` — orchestrates
  trigger → read → speak (with automatic fallback) → play, with
  press-again-to-stop and notifications at every stage.
- `EnginesConfig.qwen3_tts_model_dir`/`qwen3_tts_speaker`/
  `piper_binary_path`/`piper_voice_model_path` — new config fields.

**Fixed (found during real end-to-end testing, after the feature was
already wired up):**
- `AudioPlayer.wait_until_done()` originally had no timeout at all. On
  this test machine, a misconfigured default audio output device — a
  leftover system-level audio config from the legacy Voxtype install,
  nothing to do with Vocalis itself — made playback's wait block
  forever. From the outside this looked exactly like the AI voice engine
  being catastrophically slow, which it is not: direct synthesis timing
  confirmed Qwen3-TTS generates each sentence in 2-10 seconds. The real
  bottleneck was an audio device that opened a stream successfully but
  never actually invoked the playback callback.
  Fix: `wait_until_done()` now bounds its wait to the audio's expected
  duration plus a safety margin (`timeout_margin_seconds`, default 10s).
  If that bound is exceeded, it raises `PlaybackTimeoutError` instead of
  hanging — which `QuickReaderFeature` catches like any other playback
  failure, so the user sees a normal "Playback failed" notification
  instead of an unexplained, indefinite freeze. A follow-up fix closed a
  narrow race where a concurrent `stop()` landing in the same window as
  a timeout could misreport a real, user-initiated stop as a timeout
  error; both are covered by regression tests.

**Design corrections made along the way (recorded in the spec, not just
here):**
- The legacy `old/read-selected.sh` script actually used **Piper**, not
  Qwen3-TTS/fish-speech as this project's original design spec assumed —
  discovered by reading the actual old script before finalizing the
  design, the same way Phase 2 checked real feasibility before finalizing
  its plan.
- Qwen3-TTS's "Base" variant is a voice-*cloning* model requiring
  reference audio, not a plain default-voice TTS mode as first assumed;
  "CustomVoice" (preset voices, no cloning) is the variant actually used.

**Not yet implemented (future phases):** Document Reader, OCR, UI (tray/
widget/settings), systemd service, packaging.

**What was and wasn't verified:** Every code path — trigger/stop,
clipboard read, primary-engine synthesis, fallback-on-failure, playback,
the playback timeout itself, and every notification/failure branch — is
covered by unit tests using fake clipboard/engine/player/notifier
doubles (141 tests, ≥93% coverage, mypy clean). Qwen3-TTS's real
synthesis speed (2-10 seconds per sentence on this machine's GPU) and the
playback-hang root cause were both confirmed by direct manual testing
during this phase. What is **not** claimed here: an agent cannot
physically press Ctrl+Alt+R and listen to speakers, so the actual
press-and-listen check — does copied text really get spoken correctly,
does a second press really stop it, does NUMLOCK dictation still work
alongside it — is still the one thing only the project owner can do,
exactly as Phase 2's own changelog noted for its equivalent real-hardware
step. See this plan's "After This Plan — Manual Verification" section.

**Rollback:** additive only — Phase 0/1/2 code untouched; the only
existing-file changes are the new `EnginesConfig` fields (additive,
default-valued), `main()`'s addition of a third listener alongside the
two that already existed, and two docstring-only corrections in
`cli.py` (module and `main()` docstrings now mention the quick reader
feature they already build). Revert via `git revert` back to before this
phase's commits.
