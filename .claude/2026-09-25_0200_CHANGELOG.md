# Changelog — 2026-09-25 (Phase 3 Task 2: Qwen3-TTS primary engine)

## Vocalis Phase 3 Quick Reader: Qwen3-TTS primary voice engine

Adds `Qwen3TTS`, the primary text-to-speech voice for Quick Reader,
wrapping the `qwen-tts` package's CustomVoice model (9 preset voices,
selected by name — no reference audio/voice-cloning step, unlike the
separate "Base" variant). Implements the `ModelEngine` protocol so it
shares `ModelManager`'s single-GPU-residency policy with Parakeet.

**Added:**
- `src/vocalis/engines/qwen3_tts.py` — `Qwen3TTS`, `Qwen3TTSLoadError`.
- `tests/test_qwen3_tts.py` — 6 unit tests, 100% coverage of the new
  engine module, using a fake model object so no test touches the GPU
  or the real multi-gigabyte model.
- `pyproject.toml` — new runtime dependencies: `qwen-tts==0.1.1`,
  `transformers==4.57.3`, `accelerate==1.12.0`, `torchaudio`,

### Finding 1: onnxruntime CPU/GPU package clobbering

`qwen-tts`'s own declared dependencies pull in plain `onnxruntime`
(CPU-only), which installs into the same importable `onnxruntime`
module namespace as the `onnxruntime-gpu` package this project already
depends on for Parakeet's CUDA execution provider — whichever package
installs last wins, silently breaking GPU inference for Parakeet.

Resolution: installed `qwen-tts` with `pip install --no-deps
qwen-tts==0.1.1` (skipping its declared dependency tree entirely, since
the real runtime dependencies — torch, transformers, etc. — were
already installed explicitly per the task brief), then confirmed no
plain `onnxruntime` package was present alongside `onnxruntime-gpu`.
Verified by running `tests/test_parakeet.py` after the install and
confirming CUDA-backed inference still worked (no CPU-fallback
slowdown, no provider errors).

### Finding 2: huggingface-hub unlocks a live-network fallback in Parakeet's loader

Adding `huggingface-hub` as a project dependency (required by
`qwen-tts`/`transformers`) made it importable process-wide for the
first time. This unlocked a previously-dormant fallback path inside
`onnx_asr.load_model()` (used by `ParakeetSTT.load()`): when given a
model directory that doesn't contain valid local files, it now attempts
a live Hugging Face Hub network lookup instead of raising a fast local
error — a real regression this task's own dependency addition caused,
and a violation of this project's fully-offline, no-cloud-APIs design
rule.

Symptom: running the full test suite (or even `tests/test_parakeet.py`
alone) went from the normal ~15s to hanging 16+ minutes with real
outbound network connection attempts.

Resolution: `src/vocalis/engines/parakeet.py` now sets
`HF_HUB_OFFLINE=1` and `TRANSFORMERS_OFFLINE=1` via
`os.environ.setdefault(...)` before its own `import onnx_asr` line
(mirroring the same before-import env-var pattern `qwen3_tts.py` already
uses for `TORCH_DISABLE_NATIVE_JIT`). This forces Hub/transformers
offline mode unconditionally regardless of which module gets imported
first, so no caller needs to remember to export these vars manually.

Verified:
- `HF_HUB_OFFLINE=1 TRANSFORMERS_OFFLINE=1 .venv/bin/python -m pytest
  tests/test_parakeet.py -q` → 6 passed in 12.96s.
- The same command **without** those env vars pre-set externally →
  6 passed in 13.40s (proves the module's own `setdefault` calls are
  sufficient; no external env var needed).
- Full suite before this fix (from the prior session, unresolved):
  16+ minutes / hang. Full suite after this fix:
  **103 passed in 25.60s, 93.68% coverage.**
- `mypy src` → clean (no issues found in 19 source files).
